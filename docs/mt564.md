# `read_mt564`

*Documentation for `mt564` v0.1.0. [Back to the README](../README.md).*

> Paths such as `test/sql/data/...` in the examples refer to the extension's own test files, which are not published. Use your own files.

## Overview

`read_mt564` is a table function for SWIFT FIN **MT564** messages (Corporate Action Notification),
the batch-of-messages format produced by SWIFT Alliance / corporate-action feed exports: a sequence
of `{1:...}{2:...}{4: ...fields... -}` blocks concatenated back to back, no outer file wrapper.

MT564 is fundamentally a **nested, multiply-repeating** structure, not a flat table — read this
whole page before assuming `SELECT *` gives you everything. See "Why this can't just be one flat
row per message" below for the reasoning. General behaviour (inputs, remote files, types, NULLs,
parallelism) is described in [usage.md](usage.md).

## Quick start

```sql
LOAD '/path/to/mt564.linux_amd64.duckdb_extension';

-- One row per message (default grain), repeating blocks summarized as counts
SELECT ISIN, CAEV, CAMV, NUM_CAOPTN
FROM read_mt564('test/sql/data/mt564/mini_mt564.txt');

-- One row per election option (e.g. cash vs securities choice)
SELECT ISIN, CAOPTN_SEQ, CAOP, DFLT
FROM read_mt564('test/sql/data/mt564/mini_mt564.txt', level='CAOPTN');
```

## Message structure

```
MESSAGE (1 per "{1:...}" block)
├── GENL (singleton)          event type/class (CAEV/CAEP/CAMV), processing status
│   └── LINK (singleton)
├── USECU (singleton)          the security (ISIN block, tag 35B)
│   ├── FIA (repeats)              instrument attributes (listing venue, currency...)
│   └── ACCTINFO (singleton)
├── INTSEC (singleton)         intermediate/interim security, when the event creates one
├── CADETL (singleton)         key dates (record/meeting/effective date...)
├── ADDINFO (singleton)        free text
└── CAOPTN (repeats)          one per election OPTION offered (e.g. cash vs securities)
    ├── CASHMOVE (repeats)        cash amount/rate for this option
    └── SECMOVE (repeats)         securities movement for this option
        └── FIA (repeats)            attributes of the security being delivered
```

Fields are tagged lines: `:22F::CAEV//XMET` (qualified: tag `22F`, qualifier `CAEV`) or `:23G:NEWM`
(unqualified: tag `23G`, no qualifier). A value may continue onto following untagged lines — those
are newline-joined back onto the field.

## Why this can't just be one flat row per message

Two things repeat *independently of each other*, and one thing repeats at two different depths:

1. **`CAOPTN` repeats, and within each `CAOPTN`, `CASHMOVE` and `SECMOVE` each repeat
   independently.** They're siblings, not a related pair — an option can have cash movements,
   securities movements, or (rarely) both, in any counts. Cross-joining `CASHMOVE #2` with
   `SECMOVE #3` inside the same option would fabricate a relationship that isn't in the data.
2. **`FIA` appears at two different depths with two different meanings**: directly under `USECU`
   (attributes of the notified security) and nested under `SECMOVE` under `CAOPTN` (attributes of
   the security being delivered in that specific movement). Conflating them would silently mix two
   different things.

`read_mt564` avoids both problems with a `level=` grain selector (see below) instead of either
losing data by default or fabricating cross-products.

## The `level=` parameter

| `level=` | One row per... | Columns beyond context |
|---|---|---|
| `MESSAGE` (default) | message | `NUM_USECU_FIA`, `NUM_CAOPTN`, `NUM_CASHMOVE_TOTAL`, `NUM_SECMOVE_TOTAL`, `NUM_SECMOVE_FIA_TOTAL` counts (not the repeating data itself), plus `OTHER_FIELDS` |
| `USECU_FIA` | instrument-attribute occurrence under `USECU` | `USECU_FIA_SEQ` + that FIA's own fields |
| `CAOPTN` | election option | `CAOPTN_SEQ` + that option's own fields + `NUM_CASHMOVE`/`NUM_SECMOVE` |
| `CASHMOVE` | cash movement | `CAOPTN_SEQ` + `CAOPTN`'s own fields + `CASHMOVE_SEQ` + that movement's own fields |
| `SECMOVE` | securities movement | `CAOPTN_SEQ` + `CAOPTN`'s own fields + `SECMOVE_SEQ` + that movement's own fields + `NUM_SECMOVE_FIA` |
| `SECMOVE_FIA` | instrument-attribute occurrence of a delivered security | `CAOPTN_SEQ`/`CAOPTN` fields + `SECMOVE_SEQ`/`SECMOVE` fields + `SECMOVE_FIA_SEQ` + that FIA's own fields |

Every level also carries the same "context" columns: `BLOCK1_HEADER`/`BLOCK2_HEADER` (raw SWIFT
basic/application header), `FUNCTION` (tag `23G`: `NEWM`/`CANC`/`REPL`), `ISIN`/`SECURITY_ALT_ID`/
`SECURITY_DESC` (parsed from the `35B` block), and one column per qualifier/tag discovered under
`GENL`+`LINK`+`USECU`(direct)+`ACCTINFO`+`INTSEC`+`CADETL`+`ADDINFO`. `INTSEC` (the intermediate/
interim security an event sometimes creates, e.g. a temporary security ahead of a warrant exercise
or exchange offer's final proceeds) is treated as a singleton the same way `CADETL`/`ADDINFO` are —
only the first occurrence is read. Its own `35B` ISIN block is **not** bespoke-split like `USECU`'s
is; it comes through raw as `TAG_35B`, consistent with how `SECMOVE`'s `35B` is handled.

An unrecognized `level=` value is a clear bind-time error listing the valid ones — it does not fail
silently or fall back to a default.

### `level='MESSAGE'` (default) — one row per message

```sql
SELECT ISIN, SECURITY_DESC, CAEV, CAMV, NUM_USECU_FIA, NUM_CAOPTN,
       NUM_CASHMOVE_TOTAL, NUM_SECMOVE_TOTAL, NUM_SECMOVE_FIA_TOTAL
FROM read_mt564('examples/deep_dive.txt');
```
```
    ISIN     |                 SECURITY_DESC                  | CAEV | CAMV | NUM_USECU_FIA | NUM_CAOPTN | NUM_CASHMOVE_TOTAL | NUM_SECMOVE_TOTAL | NUM_SECMOVE_FIA_TOTAL
XS0000000018 | EXAMPLE COOPERATIVE BANK AD REGISTERED SHS     | REDO | MAND |             1 |          1 |                  0 |                 1 |                     1
XS0000000026 | EXAMPLE GLOBAL CAPITAL INCOME ACTIVE ETF UNITS | DVOP | CHOS |             1 |          2 |                  1 |                 1 |                     1
```
Message B's two `CAOPTN`s, its one `CASHMOVE`, and its one `SECMOVE` are all folded down into
plain counts (`NUM_CAOPTN=2`, `NUM_CASHMOVE_TOTAL=1`, `NUM_SECMOVE_TOTAL=1`) — none of their own
fields (`CAOP`, `CRDB`, `PAYD`...) are reachable at this level.

### `level='USECU_FIA'` — one row per instrument-attribute occurrence under `USECU`

```sql
SELECT ISIN, USECU_FIA_SEQ, PLIS, CLAS, DENO
FROM read_mt564('examples/deep_dive.txt', level='USECU_FIA');
```
```
    ISIN     | USECU_FIA_SEQ |    PLIS   |  CLAS  | DENO
XS0000000018 |             1 | EXCH/XBUL | ESVUFR | BGN
XS0000000026 |             1 | EXCH/XASX | CIOXXU | AUD
```
Both messages happen to have exactly one `FIA` under `USECU` here, so `USECU_FIA_SEQ` is `1` for
both — but a security listed on multiple venues would produce additional sequence numbers, one row
each, all sharing the same `ISIN`.

### `level='CAOPTN'` — one row per election option

```sql
SELECT ISIN, CAOPTN_SEQ, CAON, CAOP, DFLT, NUM_CASHMOVE, NUM_SECMOVE
FROM read_mt564('examples/deep_dive.txt', level='CAOPTN');
```
```
    ISIN     | CAOPTN_SEQ | CAON | CAOP | DFLT | NUM_CASHMOVE | NUM_SECMOVE
XS0000000018 |          1 |    1 | SECU | Y    |            0 |           1
XS0000000026 |          1 |    1 | CASH | Y    |            1 |           0
XS0000000026 |          2 |    2 | SECU | N    |            0 |           1
```
This is where message B's two options become two separate rows, each with its own `CAOP` and
`NUM_CASHMOVE`/`NUM_SECMOVE` — option 1 (`CASH`) has a `CASHMOVE` and no `SECMOVE`, option 2
(`SECU`) has a `SECMOVE` and no `CASHMOVE`, matching the message text exactly.

### `level='CASHMOVE'` — one row per cash movement

```sql
SELECT ISIN, CAOPTN_SEQ, CAOP, CASHMOVE_SEQ, CRDB, PAYD
FROM read_mt564('examples/deep_dive.txt', level='CASHMOVE');
```
```
    ISIN     | CAOPTN_SEQ | CAOP | CASHMOVE_SEQ | CRDB |    PAYD
XS0000000026 |          1 | CASH |            1 | CRED | 2026-05-18
```
Only message B's `CASH` option produces a row — message A has no `CASHMOVE` anywhere, and message
B's `SECU` option (`CAOPTN_SEQ=2`) has none either, so neither contributes a row at this level.

### `level='SECMOVE'` — one row per securities movement

```sql
SELECT ISIN, CAOPTN_SEQ, CAOP, SECMOVE_SEQ, CRDB_2, TAG_35B, NUM_SECMOVE_FIA
FROM read_mt564('examples/deep_dive.txt', level='SECMOVE');
```
```
    ISIN     | CAOPTN_SEQ | CAOP | SECMOVE_SEQ | CRDB_2 |                           TAG_35B                            | NUM_SECMOVE_FIA
XS0000000018 |          1 | SECU |           1 | CRED   | ISIN XS0000000018\n/GB/0000001\nEXAMPLE COOPERATIVE BANK ... |               1
XS0000000026 |          2 | SECU |           1 | CRED   | ISIN XS0000000026\n/GB/EXAMPL2\nEXAMPLE GLOBAL CAPITAL\nI... |               1
```
Two things to note here, both examples of the "Column naming and collisions" behavior described
above:
- The column is `CRDB_2`, not `CRDB` — `CRDB` was already claimed by the `CASHMOVE`-level column
  (message B's `CASHMOVE` also has a `:22H::CRDB//CRED` field), so `SECMOVE`'s own `CRDB` gets the
  disambiguating suffix. Run `DESCRIBE` for your file rather than assuming `CRDB` is always free.
- `TAG_35B` is the delivered security's ISIN block, but **raw and unparsed** — unlike `USECU`'s
  `35B`, which gets split into `ISIN`/`SECURITY_ALT_ID`/`SECURITY_DESC`, `SECMOVE`'s `35B` comes
  through as one un-split, newline-joined string. Parse it yourself if you need the delivered
  security's ISIN as a clean column (e.g. `regexp_extract(TAG_35B, 'ISIN (\S+)', 1)`).

### `level='SECMOVE_FIA'` — one row per instrument-attribute occurrence of a delivered security

```sql
SELECT ISIN, CAOPTN_SEQ, SECMOVE_SEQ, SECMOVE_FIA_SEQ, PLIS_2, CLAS_2, DENO_2
FROM read_mt564('examples/deep_dive.txt', level='SECMOVE_FIA');
```
```
    ISIN     | CAOPTN_SEQ | SECMOVE_SEQ | SECMOVE_FIA_SEQ |   PLIS_2  | CLAS_2 | DENO_2
XS0000000018 |          1 |           1 |               1 | EXCH/XBUL | ESVUFR | EUR
XS0000000026 |          2 |           1 |               1 | EXCH/XASX | CIOXXU | AUD
```
Same collision story again: `PLIS`/`CLAS`/`DENO` were already claimed by the `USECU_FIA`-level
columns (both messages' `USECU.FIA` blocks have `PLIS`/`CLAS`/`DENO` too), so the `SECMOVE.FIA`
occurrence of each gets the `_2` suffix. Note the delivered security's `DENO` (`EUR`/`AUD`) can
legitimately differ from the notified security's own `DENO` at `USECU_FIA` level (`BGN`/`AUD`) —
a redenomination or cross-currency option is exactly the case where that matters.

### `MESSAGE`-level `OTHER_FIELDS`

If a message contains a top-level block this function doesn't structurally know about (e.g. a rarer
SWIFT block type not covered by the skeleton above, such as `CAOUTC`), its fields are **not**
silently dropped — they land in the `OTHER_FIELDS MAP(VARCHAR, VARCHAR)` column, keyed by
`"BLOCKNAME.QUALIFIER_OR_TAG"`. **Scope note:** this catch-all only covers entirely unrecognized
*top-level* blocks (direct children of the message root). An unexpected block nested *inside* a
recognized block (e.g. a surprise new child of `CAOPTN`) is not currently captured — this is a
known, disclosed gap, not a silent one.

## Column naming and collisions

Dynamic columns are named after their SWIFT qualifier (`CAEV`, `RDTE`, `CRDB`, ...), or `TAG_<tag>`
for unqualified fields. The same qualifier can legitimately appear in two different structural roles
at once (e.g. `PAYD` under `CADETL`-level context *and* under `CASHMOVE`) — when that happens, the
second one gets a disambiguating suffix (`PAYD_2`). Run `DESCRIBE SELECT * FROM read_mt564(...)` to
see the actual resolved names for your file before writing queries.

## Known caveats

- **Amount fields are raw, un-split VARCHAR.** SWIFT concatenates currency and amount with no
  separator and uses a comma decimal (`:92F::GRSS//USD0,2` = currency `USD`, amount `0.2`). This
  function does not split or reparse them — `GRSS`/`NETT`/etc. come through exactly as written.
- **14-digit date+time fields (e.g. `MEET`, sometimes `PREP`) are not typed as `TIMESTAMP`.** Only
  8-digit `YYYYMMDD` fields are auto-detected as `DATE`; 14-digit values fall through to
  `BIGINT`/`VARCHAR`.
- **A date-shaped qualifier can still end up `VARCHAR`.** Some SWIFT date fields legitimately carry
  the placeholder `UKWN` ("unknown") alongside real dates; if any sampled value isn't a valid
  8-digit date, the whole column safely stays `VARCHAR` rather than risking silent per-row `NULL`s
  from failed casts.
- **Numeric-looking identifiers can get typed as `DOUBLE`/`BIGINT`.** e.g. some corporate-action
  reference numbers (`CACN`) look like `"23.08659"` and pass the generic numeric-detection
  heuristic. Use `all_varchar=true` or check `DESCRIBE` output if this matters for your query.
- **`nullstr`/`empty_as_null` don't apply to the four bespoke columns** (`FUNCTION`, `ISIN`,
  `SECURITY_ALT_ID`, `SECURITY_DESC`) — only to the dynamically-discovered qualifier columns.

## `read_mt564` options

| Option | Type | Default | Behavior |
|---|---|---|---|
| `level` | `VARCHAR` | `'MESSAGE'` | Output grain; one of `MESSAGE`, `USECU_FIA`, `CAOPTN`, `CASHMOVE`, `SECMOVE`, `SECMOVE_FIA`. See table above. |
| `nullstr` | `VARCHAR` or `LIST<VARCHAR>` | unset | Trimmed values equal to one of these markers become `NULL`. Applies to dynamically-discovered columns only (see caveats). |
| `empty_as_null` | `BOOLEAN` | `false` | Converts empty strings to `NULL`. |
| `all_varchar` | `BOOLEAN` | `false` | Forces dynamically-discovered columns to `VARCHAR` instead of inferred types. |
| `auto_detect` | `BOOLEAN` | `true` | Infer dynamically-discovered column types from sampled messages. |
| `sample_size` | `BIGINT` | `2000` | Number of **messages** (not rows) sampled for schema/type discovery. `<= 0` means "sample every message". |
| `filename` | `BOOLEAN` | `false` | Appends a `filename` output column. |
| `hive_partitioning` | `BOOLEAN` | `false` | Extract path segments `key=value` into output columns (as `VARCHAR`). |
| `parallel` | `BOOLEAN` | `true` | Scan multiple files on multiple threads (row order across files is then unspecified; `false` keeps file order). |

`path` may be a file, directory, glob or a `LIST` of them, and a bare `.mt564` / `.mt564.gz` path in `FROM` is
read with `read_mt564` automatically. Remote paths (`s3://`, `https://`, ... via `httpfs`) work as explicit file
paths. `nullstr` markers are ignored by type detection. Zero-padded numbers (`CAON` `001`) are detected as
numbers, because SWIFT zero-pads genuine numeric fields.
`OTHER_FIELDS` lists unrecognized blocks in document order.

## Multi-file behavior

When scanning multiple files (glob or directory), the dynamic-column vocabulary (context and each
`level`'s own fields) is discovered across all matched files' sampled messages — a qualifier present
in one file but not another simply comes through as `NULL` where it's absent, no extra flag needed.
